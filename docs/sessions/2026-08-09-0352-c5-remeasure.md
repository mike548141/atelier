# 2026-08-09 · 0352 UTC · C5 re-measured — one premise false, one defect underneath (Opus, wt: c5-remeasure-0809)

Mike asked for work on C5 and anything blocking it. C5 is a ruling owed, so the
blocking work was the measurement: the 2026-08-04 ruling was executed and
reverted within hours of landing when three premises failed on contact, and
none of the three had been checked against the real artefacts before the
ruling was sought. This session ran that sweep — every plane, every repo on
the machine — and put the re-ruling back to Mike with costs instead of

Probed with a scratch term list via `$ATELIER_LEAKSCAN_TERMS`. The operator's

execution: a machine-local scanner config binds every repo and every plane,
so it must be probed that way and never edited to find out.

## The three premises

**(a) The full-tree red stands, smaller and differently shaped.** 67 findings
here, not the 86 on record — and **60 of the 67 are frozen records**
(`sessions/`, `reviews/`, `SESSIONS.md`, `ROADMAP-DONE.md`, `CHANGELOG.md`).
Only **7** sit in live, editable files. What read as a whole-repo problem is a
records problem, which matters because records are exactly what a scoping
mechanism can address and rewording cannot.

**(b) The ordinary-English premise stands, and is now three shapes rather than
one.** Rare — 3 instances against ~673 name uses estate-wide — but the shapes
differ in what they permit. One is a rewordable docstring in this repo. One is
a **verbatim quotation from an upstream bug report** in a child, which cannot
be reworded without falsifying the quote. One is a **physical building** in a
property inventory. The last two are the durable argument: a guard whose only
hatch is "reword the sentence" can serve neither a quotation nor a real-world
noun.

**(c) FALSE — and it is the premise that killed the ruling.** The claim was
that the estate root's own self-references would hard-block under D1 with no
in-repo hatch. They do not. That repo **retired leakscan repo-wide by ADR on
2026-07-13**, a month before the ruling, and two further permanently-private
personal repos have since made the same call. `.leakscanignore` filters at the
**path** level *before* the term list runs, on the staged plane as well as the
tree plane — the `_ignored` calls in `tools/leakscan.py` sit ahead of
`scan_text` on both paths, and the staged branch says so in a comment. So D1
never reaches those trees at all. Verified rather than reasoned: all three
scan **clean, exit 0**, with the bare term live. The count on record was also
wrong (492, not ~364), which is the sixth time a figure on this programme has
been wrong — as always, in both directions.

## What no premise modelled

The term also binds **six private children that doctrine positively instructs
to name the estate root** — `PROPAGATION.md`'s name↔posture split puts the
name in a private child's own onramp — for **58 lines** between them. A bare
term makes the prescribed act red in the repos that were told to do it. That,
not the frozen records, is the sharpest cost, and it appears in none of the
four options as they were written.

## The defect underneath, surfaced by Mike's exception ruling

Mike restated his standing rule mid-session: every guardrail exception must be
as narrow and specific as possible, must record **why** it is safe, and must
record **when** it was granted. That is already doctrine —
`GUARDS.md` ranks allowances Line < Check < Repo and requires the narrowest
level that covers the case, and its *acceptance vs deferment* split governs
whether a date is a grant stamp or an expiry.

Held against that ladder, the term list fails structurally: **it has no narrow
hatch.** The **Line** level does not exist for terms — D1 (2026-08-04) ruled
that allow-markers never exempt the term list — so the narrowest *available*
level is **Check**, and `.leakscanignore` is not rule-scoped. Its own docstring
calls it "the widest allowance this scanner grants": a whole path, every rule,
indefinitely. There is no way to say *this one term does not apply here*. D1
removed the narrow hatch without putting a narrow replacement in its place, and
every term-list false positive has been paying that since.

**The estate has already paid it once.** A public place name was deleted from
the term list outright (2026-08-06) because it was the only term that could not
be made to pass a product tree without an over-broad path ignore. The right
answer was a narrow reasoned exception; none could be written, so a term that
should still guard everywhere else was dropped instead. C5 is the second
instance of one defect, not a new problem.

The three repo-wide `*` opt-outs found by the sweep were checked against the
same bar rather than assumed compliant. Each is a genuine *acceptance* whose
premise is inverted — a permanently-private repo that is the deliberate home
for exactly the data the scanner hunts — so the whole repo is the narrowest
scope that covers the case, and each carries its reason plus a dated ADR. They
pass. Recorded because a `*` should never pass unexamined.

## A second finding: the verdict has two states and needs three

Mike named the model the guards are meant to follow — find everything, report
them all, subtract the ones that are well-reasoned and fully recorded, then
give an honest final verdict. The first three steps are built and good. The
fourth is not: `render_human` branches on `not findings` alone, so
`✓ leakscan clean` covers two materially different situations — nothing was
found, and everything found was forgiven. Not a corner case. This repo's own
live run subtracts **35 findings by allow-marker plus 7 files by glob** and
still headlines `clean`; a permanently-private repo scanned with `*` prints
`✓ leakscan clean (structural + local)` with **99 files never opened**. The
`suppressed:` line beneath is honest; the verdict word above it is not, and the
verdict is what a tired session and a CI log actually read.

Roadmapped rather than built: it touches every scanner and every adopting tree,
the same blast-radius argument that held G3 back for its own landing. Exit
codes do not move (0 for both clean and all-accepted, 1 for live findings), so
the change is text plus one added JSON field — `clean` stays as it is, since
consumers read that key today.
