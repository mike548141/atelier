# Fable review — linkscan (the internal-link integrity check)

**Status:** brief (ask on top). Verdict appended below the divider after the
review runs. **Run this cold** — a fresh session, not the window that built it
(`REVIEW.md`: independence is about context, not just model tier; the builder's
reasoning must not ride along).

Range under review: **the commit that adds `tools/linkscan.py`,
`tools/test_linkscan.py`, and the `tools/README.md` linkscan section** (atelier
HEAD at brief time — `git log --oneline` names it). Self-contained, in-repo, no
machine-local artifact this time (unlike the create-repo skill).

**Why it earns a review before it becomes a gate.** linkscan is net-new tooling
in the same class as the scan triad: a check destined for CI and the pre-commit
hook, where a clean exit is read by automation as "safe". Session 23 deliberately
deferred it as "net-new tooling wanting its own review, not stacked onto the CI
change". It is **not yet wired into `ci.yml` or `pre-commit.sample`** — that
wiring is held for this verdict (the don't-stack-a-gate-on-unreviewed-tooling
rule, third application after the method layer and the create-repo mechanism).
The failure mode that matters most is the **false negative**: a real broken
pointer the scanner doesn't see, reported as green. atelier's whole architecture
is pointers; a link check that silently misses breaks is worse than none, because
it manufactures false confidence in exactly the graph the doctrine leans on.

## What the work is (context for the reviewer)

Read first: `method/PROPAGATION.md` (why pointers are load-bearing),
`tools/leakscan.py` (the house-tool pattern linkscan copies —
`Finding`/`--selftest`/`.­­*ignore`/allow-marker/fail-safe exit codes), the
"What these scans cannot see" residual list at the top of `tools/README.md`, and
the linkscan section further down.

- **The tool.** `tools/linkscan.py` — walks Markdown (`.md`/`.markdown`), extracts
  inline `[text](dest)` / `![alt](dest)` destinations, and checks each *internal*
  link. Two finding kinds: `missing-file` (path doesn't resolve, relative to the
  linking file or repo root for `/…`) and `missing-anchor` (a `#fragment` into a
  Markdown target — or same-file — whose GitHub slug matches no heading). External
  schemes and `//host` are skipped; `#L42` line anchors and anchors into
  non-Markdown targets are not validated. Fenced/inline code is stripped so
  example links don't false-positive. `linkscan:allow` + `.linkscanignore` hatches.
  Exit `0`/`1`/`2` fail-safe.
- **The slugger.** `slugify()` is a *simplified* GitHub anchor algorithm: unwrap
  inline code/links/emphasis → lowercase → drop non-`[\w\s-]` → spaces to hyphens,
  with `-1`/`-2` disambiguation for repeated headings. Deliberately not a full
  CommonMark renderer.
- **The tests.** `tools/test_linkscan.py` — 26 stdlib tests: slugify edge cases,
  duplicate-heading suffixes, fence/inline-code stripping, allow-marker,
  target-split, angle-bracket + titled destinations, and an end-to-end suite over
  a throwaway doc tree (relative up/down, root-relative, dir targets,
  anchor-into-non-markdown, ignore glob, missing file/anchor). Suite 145→171.
- **Proven live.** `--selftest` OK; ran over the whole atelier tree — clean (55
  Markdown files, 36 internal links). Anchor pass/fail verified against a real
  file via a temp probe (`../README.md#atelier` passes; a bogus fragment flags);
  a deliberately broken file/anchor flags. The tree carries **zero** anchored
  internal links today, so the anchor path has no real-tree exercise — only
  selftest + unit tests + the throwaway probe cover it. Flagged honestly here.

Out of scope (note, don't spend budget): the scan triad and other tools (already
reviewed / their own briefs); whether to *also* build reference-style-link support
(judge whether the stated residual is honest, not whether to expand scope now).

## Scope — three lenses, run all three

1. **False-negative surface** (most important): what real broken internal link
   shapes does this miss, and are they all named in the residual list? The
   `tools/README.md` residual claims reference-style links, HTML links, setext
   headings, two-line-spanning `](…)`, and slugger divergence are the known gaps.
   Attack that list — is it complete, and is each gap acceptable or a hole?
2. **Correctness & honesty**: does the slugger match GitHub closely enough that a
   *valid* anchor is never flagged (false positive → alarm fatigue → the tool gets
   disabled)? Does path resolution handle the cases atelier actually uses
   (sibling, `../`, `/root`, directory targets, `%20`)? Any claim stronger than
   its evidence.
3. **Fit as a gate**: is it safe to wire into CI + the pre-commit hook? Is exit-2
   truly reserved for "couldn't complete" (never a silent green on a scan that
   half-ran)? Does the fenced/inline-code stripping ever *over*-strip and hide a
   real link that lives beside code?

## Load-bearing assumptions to attack

If any is false, the check is mis-built no matter how clean the prose.

1. **The slugger never flags a valid anchor.** A false positive on a live link is
   the tool's worst outcome short of a false negative — it trains the author to
   ignore it or `allow`-mark real breaks. Find a heading atelier could plausibly
   write whose real GitHub slug ≠ `slugify()` output (punctuation, emoji, numbers,
   `&`, code+text mix, duplicate collision ordering).
2. **Fenced/inline-code stripping is line-accurate and side-effect-free.** The
   fence tracker keys off ` ``` `/`~~~` at line start after `lstrip`. Does an
   indented fence, a `~~~`-vs-` ``` ` mismatch, or a fenced block that's never
   closed (runs to EOF) cause it to swallow real links after it — or miss a link
   *inside* what it wrongly thinks is code?
3. **Path resolution matches how a reader/GitHub resolves the link.** Relative to
   the *linking file's directory*, root for `/…`. Is there a case where linkscan
   says "resolves" but a GitHub reader gets a 404 (or vice-versa) — e.g. a link
   into `.git`-adjacent paths, a symlink, case-sensitivity, a target that exists
   as a dir *and* the link implies a file?
4. **The `](…)` regex catches every inline link atelier writes.** It requires
   `](` then a bracketed-or-non-space destination on one line. What does it miss —
   destinations with a balanced `)` inside, a link split across lines, an image
   reference — and are those all in the residual?
5. **A degraded/errored scan is never reported green.** Unreadable file
   (decode-errors → replace), a path arg that doesn't exist, an empty tree. Does
   any of these exit 0 while having scanned nothing it claimed to?

# Verdict — PASS-WITH-FINDINGS (Fable, 2026-07-10, cold session)

## The floor, re-run not read (REVIEW: re-run every live-proven claim)

All reproduced at review start, before any change: `--selftest` OK ·

## Findings

**L1 — a typo'd path arg scanned nothing and reported clean. [fixed] (assumption
5 broken — the worst gate-fit defect here).** `linkscan does-not-exist` walked an
empty `rglob`, found no files, and exited **0** — proven live. Wired into a hook
or CI with a mistyped path, it would have reported green forever while checking
nothing: the exact silent-success defect EVIDENCE §14 exists to kill. Fixed: a
named path (or `--root`) that doesn't exist is now a usage error, exit 2, message
to stderr. Pinned by two tests.

**L2 — a case-mismatched link passes locally and 404s on GitHub. [fixed] (false
negative, assumption 3).** `[x](target.md)` against on-disk `Target.md`: APFS is
case-insensitive, so `exists()` said yes and the scan ran green — proven live —
while every GitHub reader gets a 404. CI (case-sensitive ubuntu) would catch it,
but the pre-commit hook — the control that's supposed to catch it *first* — runs
on the Mac. Fixed: on-disk casing is walked component-by-component and a mismatch
reports the true name (`case mismatch — on-disk name is 'Target.md'`).
Unicode-normalisation-only differences (APFS stores NFD, links are NFC — the
macron case) are deliberately *not* mismatches, so te reo filenames can't false
positive.

**L3 — a link escaping the repo root passes if the file happens to exist on this
disk. [fixed] (false negative, assumption 3).** `[x](../outside.md)` resolved
against a sibling that exists locally — green, proven live — but GitHub serves
nothing above the repository root, so it is a 404 for every reader. In a repo
whose own doctrine involves sibling-repo pointers (`../atelier`), this shape is
not hypothetical. Fixed: new finding kind **`outside-root`**; a deliberate
machine-local pointer takes a `linkscan:allow` with its reason, which is the
honest shape for it.

**L4 — anchor matching was lenient where GitHub's is exact. [fixed] (the false
negative the brief feared most, assumption 1's dual).** The check compared
`slugify(anchor)` against the slug set, so `#A-Section` matched heading "A
Section" and scanned green — proven live — while GitHub fragment matching is
exact and the reader lands unscrolled. Fixed two-tier: exact match first; if only
the re-slugged form matches, that's a finding *with the fix in the detail*
(`heading exists but anchors match exactly — write '#a-section'`). This required
fixing the slugger first (next finding), or the tightening would have minted new
false positives.

**L5 — the slugger stripped literal underscores; GitHub keeps them. [fixed]
(assumption 1 — the hunted false-positive class, found).** `slugify` deleted
every `_` as emphasis markup, so heading `snake_case name` slugged to
`snakecase-name` while GitHub mints `snake_case-name`. Under the old lenient
compare the double-slugify masked it; under L4's exact compare it would have
flagged every valid underscore anchor. Fixed: underscores unwrap only as flanking
emphasis (`_emph_`), literal `snake_case` survives. Selftest now pins it.

**L6 — a parenthesised filename mis-parsed and flagged a working link. [fixed]
(false positive, assumption 4).** `[x](a(1).md)` captured dest `a(1` — proven
live (`[missing-file] a(1`) — training exactly the alarm-fatigue the brief names.
The destination regex now takes one level of balanced parens (a legal filename
shape); an *unbalanced* paren destination stays invisible, which matches GitHub
(it won't parse it as a link either).

**L7 — the fence tracker mis-tracked nested and info-string fences. [fixed]
(assumption 2 broken).** Two shapes proven live: a ``` inside a ```` block
"closed" the fence, so the example link between the inner markers was read as
live text and flagged; and a ```` ```python ```` line inside an open ``` block
did the same (CommonMark: a closing fence carries no info string). The dual
shape — a *real* link swallowed after an odd number of mis-toggles — is the
false-negative twin. Fixed: one shared `_content_lines` tracker (link extraction
and heading collection can no longer drift), closing only on the same character,
a run at least as long, bare of info string. The unclosed-fence-to-EOF behaviour
was checked and **kept** — it matches GitHub (code to end of file), now pinned
by a test so nobody "fixes" it later.

**L8 — root-relative `/…` semantics verified against GitHub, not assumed.
[verified, no change].** The brief's probe list flagged it; GitHub's own docs
confirm: "Links starting with `/` will be relative to the repository root." The
tool's handling matches. The tree carries zero such links today, so this was a
latent claim — now a grounded one.

**L9 — setext-headed targets false-positived; the residual had it filed under
the wrong failure class. [fixed].** A valid link into a `===`-underlined heading
flagged `missing-anchor` — proven live. The residual list *did* name setext
honestly, but as an invisibility (false-negative flavour), when the live effect
was a false positive on a correct link — assumption 1's alarm-fatigue class.
Fixed by parsing setext headings conservatively (paragraph line + underline,
adjacent lines, list/quote/table shapes excluded); the house `---` divider after
a blank line mints nothing, pinned by a test. Setext is off the residual list
because it's now covered.

**L10 — degraded-scan tiers tidied; indented code stated as the residual it is.
[fixed / stated].** An unreadable file now exits 2 with a message instead of an
uncaught traceback (it was never a silent green — interpreter exit — but the
"couldn't complete" tier is now honest). And a link-shaped example inside an
**indented (4-space) code block** is read as live text — a false positive proven
live, **deliberately not fixed**: skipping 4-space-indented lines would skip real
links in nested list items, and a stated FP that costs one allow-marker beats a
silent FN. It's on the residual list now, alongside the HTML-minted-anchor FP
(`<a id>`, `<h2>` targets) which the old list also missed.

## Lens answers

1. **False-negative surface:** the residual list was honest but incomplete, and
   the sharpest FNs weren't on it because they were *bugs*, not scope: L2 (case),
   L3 (outside-root), L4 (exact anchors), L7's swallow-shape. All fixed rather
   than stated — they were cheap to fix and expensive to carry. What remains
   stated is genuinely structural (reference-style, HTML, two-line `](…)`,
   slugger-divergence exotica).
2. **Correctness & honesty:** the slugger now matches GitHub on every shape
   probed (underscores were the one real divergence found; emoji, em-dash, `&`,
   code-in-heading, duplicates, macrons all verified matching). Path resolution
   verified for sibling, `../`, `/root` (against GitHub's documented semantics),
   dir targets, `%20`. The "proven live" claims in the brief all reproduced.
3. **Fit as a gate:** **safe to wire now** — with L1 fixed, exit 2 is truly
   reserved for couldn't-complete, and a scan that runs reports what it dropped.
   The code-stripping was probed for over-stripping both ways; the one real
   link-beside-code hazard (inline code) was already handled, and fences now
   track correctly.
