## Scope — four lenses over the whole commitment

1. **Approach & assumptions.** The load-bearing choices to attack: an
   expired advisory reds the board but never blocks; the legacy bare-list
   spelling parses through the transition; `review-by` validated as a real
   ISO date at parse so downstream ageing is a string compare; A1(b)'s
   `why` required only for boundary/integrity scanners; legacy scope lists
   exempt from the `why`. Each is a ruling or an applier choice — test that
   the code matches the stated rule and that the rule's edges hold.
2. **Correctness & quality.** Parse/validate edges: unknown keys, missing
   halves, malformed and impossible dates, the legacy/new-spelling
   boundary, `__post_init__` normalisation (no internal stage should ever
   see the union type), expiry comparison correctness (string compare
   demands zero-padded ISO), the days-standing arithmetic, JSON round-trip
   of the new `Result` fields, and whether the tests pin behaviour or
   mirror implementation.
3. **Completeness / harvest.** Does every reporting surface carry the new
   states (floor render, `--json`, fleet board, CI annotations)? Does the
   CONTRIBUTING template teach the new schema? Is anything the schema
   change owes (phase 2's blocker, the migration) honestly deferred rather
   than silently dropped?
4. **Security & privacy.** The parser widens: new nested-object config
   shapes from repo-supplied JSON. Attack: type-confusion on the new
   shapes, a `why`/date echoed unescaped into CI workflow commands
   (the LS1 class), date parsing as a DoS/crash surface, and whether an
   expired-but-green-exit advisory can be used to hold a *boundary* check
   soft indefinitely (interaction with the no-advisory-form rule).
   `/security-review` reach: landed-delta review, no pending diff to aim
   it at — discharged on those grounds; the mechanical floor is the scan
   and test suites, re-run live.
